Key Code Excerpts

Although the full implementation is available in the repository, a few excerpts help illustrate the mechanics behind the automation layer. The example below shows how the autosave routine guards against overlapping runs and then delegates world persistence to a dedicated function that commits the updated data to Git.

scripts/autosave.sh

View on GitHub

#!/bin/bash
# Periodic backup, run every PERIODIC_INTERVAL minutes while the server is up.
# Can also be run by hand: docker compose exec minecraft /opt/minecraft-backup/scripts/autosave.sh

source /opt/minecraft-backup/utils/saveWorld.sh

LOG_FILE="$LOG_DIR/autosave.log"

exec 9>"$LOCK_FILE"

if ! flock -n 9; then
  log "AUTOSAVE" "Another backup is still running. Skipping."
  exit 0
fi

if ! server_online; then
  log "AUTOSAVE" "Server is not accepting RCON commands yet. Skipping."
  exit 0
fi

log "AUTOSAVE" "Starting execution..."

if ! saveWorld "AUTOSAVE"; then
  log "AUTOSAVE" "Execution failed."
  exit 1
fi

log "AUTOSAVE" "Execution completed."

utils/saveWorld.sh

View on GitHub

# Flushes the world to disk (when the server is running), commits every change and pushes it.
saveWorld() {
  local prefix="$1"
  local online=false

  # ... ensure_repo prepares the repository (omitted)

  if server_online; then
    online=true

    rcon 'tellraw @a {"text":"📂 Backup started!","color":"gold"}' >/dev/null

    # Pause automatic saving so region files are not rewritten while they are staged.
    rcon save-off >/dev/null
    rcon save-all flush >/dev/null
  fi

  local add_status=0
  repo_git add -A || add_status=$?

  if [ "$online" = true ]; then
    rcon save-on >/dev/null || log "$prefix" "WARNING: could not re-enable automatic saving."
  fi

  if [ "$add_status" -ne 0 ]; then
    log "$prefix" "ERROR: git add failed."
    return 1
  fi

  if repo_git diff --cached --quiet; then
    log "$prefix" "No changes since the last backup."
  else
    local commit_msg
    commit_msg="$(date -u +"%Y-%m-%dT%H:%M:%SZ") - $prefix"

    repo_git commit -q -m "$commit_msg" || return 1
  fi

  # Also sends commits left behind by previous failed pushes.
  if ! repo_git push -q -u origin HEAD; then
    log "$prefix" "ERROR: git push failed."
    # ... warns the players in game (omitted)
    return 1
  fi

  log "$prefix" "Backup successfully pushed."
}

utils/common.sh: credentials

View on GitHub

The token is handed to Git through an inline credential helper defined in environment variables, so it never reaches the remote URL, a config file or the logs:

export GIT_TERMINAL_PROMPT=0
export GIT_CONFIG_COUNT=3
export GIT_CONFIG_KEY_0="safe.directory"
export GIT_CONFIG_VALUE_0="$REPO_DIR"
export GIT_CONFIG_KEY_1="init.defaultBranch"
export GIT_CONFIG_VALUE_1="$GIT_BRANCH"
export GIT_CONFIG_KEY_2="credential.helper"
export GIT_CONFIG_VALUE_2='!f() { test "$1" = get && test -n "$GITHUB_TOKEN" && echo "username=${GITHUB_USER:-x-access-token}" && echo "password=$GITHUB_TOKEN"; }; f'

These sections illustrate the predictable structure that supports periodic and manual world preservation. The underlying model is intentionally minimalistic so the logic remains transparent and easy to debug, while every step reports failures instead of assuming success.

Persistent digital environments demand predictable behaviour. Whether managing corporate infrastructure or personal projects, stability depends on systems that continue to operate even when attention shifts elsewhere. Over time I realised that reliable automation is not only relevant in professional settings. It can also solve surprisingly ordinary problems.

A practical example emerged in my own home. My partner and I often play Minecraft together and our sessions sometimes last several hours. Anyone who has hosted a local or containerised server knows that crashes or unexpected shutdowns can corrupt the world or erase progress. After losing entire builds on more than one occasion I started thinking seriously about how to design a stable and automatic backup mechanism that would remove the risk altogether.

This line of thinking eventually led to a full architecture that integrates Docker, Git and GitHub for continuous world versioning. Although this post uses that implementation as a reference, the focus here is the reasoning that guides the creation of automation pipelines that are reliable, observable and resilient.

Designing the Automation Flow

Before exploring each script it is useful to visualise how the overall workflow operates. The intention was to create a loop that could run indefinitely, independent of the user’s attention.

This diagram reflects the core concept. Every event leads to a deterministic and observable action. World data is always saved, always committed and always pushed, and any step that fails is logged and reported instead of silently ignored.

Understanding the File Structure

The project uses a modular structure that separates concerns and creates predictable behaviours. Each file contributes uniquely to the automation pipeline.

.
├── .github/workflows/ci.yml   # ShellCheck, Hadolint, compose validation and image build
├── docker-compose.yml
├── Dockerfile
├── entrypoint.sh              # Startup → periodic loop → graceful shutdown
├── .env.example
├── scripts
│   ├── autosave.sh            # Periodic backup (can also be run by hand)
│   ├── init.sh                # Restores/clones the world before the server starts
│   └── shutdown.sh            # Final backup after the server stops
└── utils
    ├── common.sh              # Shared configuration, git/RCON helpers
    ├── log.sh                 # Logging to stdout and ./logs
    └── saveWorld.sh           # Flush → commit → push

Each one will be explained individually so the full picture becomes clear.

Container and Image Definitions

docker-compose.yml

Defines how the server is launched. It handles:

  • Port exposure for gameplay only (MC_HOST_PORT, 25565 by default). RCON stays inside the container, since backups are the only thing that uses it;
  • Environment variable loading;
  • Persistence of the Minecraft world and logs;
  • Building the custom image from the local Dockerfile;
  • A three minute stop_grace_period, so Docker does not kill the container while the final backup is being pushed.

Its purpose is to maintain stability across restarts and ensure that all automation scripts remain present inside the container.

Dockerfile

The Dockerfile extends the “official” image itzg/minecraft-server:java25 (configurable through MC_IMAGE_TAG for older Minecraft versions) then installs all custom scripts under /opt/minecraft-backup. This combination provides the reliability of a well maintained base image while enabling custom behaviour controlled entirely by our own entrypoint.

This duality of stability and customisation supports the idea of predictable infrastructure that can also adapt to specific needs.

Core Execution Orchestrator

entrypoint.sh

This script coordinates the lifecycle of the server and backup system.

It performs:

  1. Configuration validation (repository name, token, interval);
  2. Initialisation and startup synchronisation;
  3. Launch of the periodic autosave loop;
  4. Delegation to the official Minecraft server start script;
  5. Graceful shutdown: the server is stopped first, then the final backup runs.

A second diagram helps illustrate this behaviour.

This flow ensures that no world data is lost, regardless of how the container stops. The same final backup also runs when the server stops on its own, for example after /stop in game.

Utility Layers

utils/common.sh

Shared configuration used by every script: the Git identity (commits fail without a committer), the credential helper shown above, RCON helpers and a function that runs Git as the same user as the server, so no world file ends up owned by root.

utils/log.sh

A lightweight logger that standardises how each script communicates events. Every log entry includes a timestamp and prefix and goes both to docker compose logs and to persistent storage, so it survives container recreation. This improves verification and troubleshooting.

utils/saveWorld.sh

The most responsibilities in the automation pipeline concentrate here. It performs:

  • In game world flush via RCON, with automatic saving paused while files are staged
  • Git staging and committing (only when something changed)
  • Push synchronisation with GitHub, including commits left behind by earlier failed pushes
  • Messaging for both users and logs

It represents the core reliability mechanism. If this script functions correctly, every world state becomes recoverable.

Lifecycle Scripts

scripts/init.sh

Executed only during startup. It validates the remote repository, checks whether it exists and whether it is empty. It clones the repository, fast-forwards an existing clone or prepares a new one so the world directory becomes fully managed by Git. A local world without history is moved aside instead of being overwritten. This step prevents drift between the running server and the stored history.

scripts/autosave.sh

Runs periodically based on the interval defined in the environment variables. It skips the run when another backup is still in progress or the server is not ready yet, and otherwise calls saveWorld.sh. These periodic commits create a complete backup timeline.

scripts/shutdown.sh

Triggered after the server has stopped. It waits for any backup still in progress and calls saveWorld.sh so the final server state is stored safely. Because the server has already flushed the world to disk, this prevents data corruption and makes the server restart friendly regardless of how the container was stopped.

Environment Templates and Management

.env.example

Guides the user in defining:

  • GitHub repository credentials (a fine-grained token limited to the backup repository is enough)
  • Minecraft server settings and the base image tag
  • Backup intervals and an optional Git remote other than GitHub
  • Metadata for commits

This separation of configuration strengthens clarity and reduces accidental misconfiguration, and the entrypoint refuses to start with an invalid one.

Why This Matters

Although the technical implementation is interesting, the motivation emerged from a real problem. Playing Minecraft with my partner is one of our favourite activities and losing progress due to corruption or abrupt shutdowns was frustrating. Manual backups were easy to forget and relying on memory alone was not sustainable.

Creating an infrastructure that handles backups automatically removed the cognitive load entirely. It also ensured that every session became safe. The system evolved from a personal inconvenience into an elegant example of how automation thinking can improve both professional and personal digital environments.

This project demonstrates that reliable systems do not appear spontaneously. They are built through reasoning, testing and iteration. The first version already worked for everyday use, yet running it for months revealed failures that only appear over time: commits that failed without a committer identity, a token that leaked into the logs, a final backup racing against the server’s own shutdown. Whether used for game worlds, business processes or experimental environments, the principles remain consistent: predictable automation, clear observability and robust fallback mechanisms.

Final Considerations

Constructing automation flows like this establishes a foundation for trust in any persistent system. Once the structure works without supervision, users are free to focus on the experience rather than maintenance. In my case it allowed long sessions of building and exploration with my partner to continue without disruption.

I hope this explanation clarifies not only what the system does, but also how it was structured and why the reasoning behind it led to a reliable design.
