Abstracting and Generalising Executors for Modular Game Loops

How small units of intention, composed into sequences, turn a game loop into something you assemble instead of rewrite

Game Development
Software Architecture
Systems Design
Design Patterns
An engine-agnostic look at executors, sequencers and event-driven flows that make game loops modular, plus a classified way to organise the project around them.
Author

Daniel Torquato

Published

November 17, 2026

At the gameplay level, a game is an ordered set of moments: the player walks a few steps, looks around, approaches a door, a scene plays, something appears in the dark. Each moment has a precondition, a completion condition and side effects on the world. When those moments are scripted directly against each other, the flow is spread across flags, timers and callbacks in many places, and any change in order or content becomes a refactor.

This article describes an architecture that addresses this by treating every moment of the game as an executor: a unit with a uniform lifecycle and an explicit completion event, orchestrated by generic components that know nothing about what each executor does. It covers:

  • The executor contract and its lifecycle;
  • Composition through sequencers and the capabilities a child can expose;
  • Aggregation, readiness barriers and interactions as event sources;
  • Data-driven variation;
  • Extensions of the model (parallelism, selection, cancellation, shared context);
  • A classified segmentation of the project that keeps these boundaries intact.

The examples come from a horror game, but nothing here depends on a genre, an engine or a programming language. Every flow is described as a diagram so that it can be translated to any toolset.

The Problem with Hardcoded Game Loops

Before talking about the solution, it is worth visualising the problem. The most common way to script a sequence of gameplay moments is to let each piece know what comes next.

Every arrow in this diagram is a dependency. The door knows about the cutscene, the cutscene knows about the encounter, and every script reads or writes flags that others left behind. The flow exists, but it exists implicitly, spread across the pieces, and nobody can read it in a single place.

The consequences are predictable:

  • Reordering two moments requires editing every script around them;
  • Reusing a moment in another level drags its neighbours along;
  • A missing object halfway through silently freezes the whole sequence;
  • Testing one moment in isolation is nearly impossible.

What we want is the opposite: pieces that know nothing about each other, and a flow that is described explicitly, in one place, by something whose only job is to run it.

The Executor: The Smallest Unit of Intention

An executor is anything that represents one thing that must happen: wait for the player to walk ten metres, play an animation, spawn a creature, wait until a light is switched off. What makes it an executor is not what it does, but the contract it follows:

  1. It can be started;
  2. While running, it can update itself, every frame or every tick;
  3. At some point it decides it is done and announces that it has finished.

That contract can be modelled as a tiny state machine:

Three states, two transitions that matter. The executor does not know who started it, and it does not know what comes after it. It only knows its own completion condition.

Lifecycle hooks

To avoid every executor reimplementing the same state handling, the base executor owns the state machine and exposes only hooks for the specific behaviour, a classic application of the Template Method pattern1:

The concrete executor never touches the state directly. It prepares what it needs when it starts, measures its own progress while running, calls finish when its condition is met and cleans up afterwards. Everything else is guaranteed by the base.

A few examples of how different moments fit the same shape:

Executor On start On update Completion condition On finish
Walk Show a movement hint Accumulate horizontal distance travelled Distance ≥ N metres Remove the hint
Look around Show a camera hint Accumulate absolute rotation Rotation ≥ N degrees Remove the hint
Get close Place a marker on a target Measure distance to the target Distance ≤ N metres Remove the marker
Cutscene Lock controls, play animation Nothing Animation finished event Restore controls

Notice that the last row has no update logic at all. Its completion comes from another event, which already hints at something important: executors can finish because of time, because of player progress or because something else in the world told them to.

Fail Forward: Executors That Never Deadlock

Games run in messy environments. Objects get renamed, a target is removed from a level, an asset fails to load. In a hardcoded flow, any of these freezes the sequence forever, usually without an error.

Executors can adopt a simple rule: if an executor cannot do its job, it finishes immediately.

The sequence always moves forward. A missing marker means the player does not see a hint, not that the game stops.

TipFail forward or fail stop?

Skipping is the right default for presentation (hints, markers, ambience). For moments that carry state the rest of the game depends on, such as giving the player a key, skipping silently only moves the bug further away. Make the choice explicit per executor and always log the skip, so a broken moment shows up in the logs instead of in a player’s review.

The Sequencer: An Executor of Executors

With a uniform contract in place, the orchestrator becomes almost boringly simple. A sequencer holds an ordered list of executors and runs them one after the other:

The sequencer subscribes to the finished event of the current executor once, starts it and waits. When the event arrives, it moves to the next one. When the list is over, it announces that it has finished.

And that last detail is where the idea becomes powerful: a sequencer follows the same contract as an executor. It can be started and it announces when it is done. So a sequencer can be placed inside another sequencer, exactly like any other executor, which is the Composite pattern2 applied to gameplay flow.

The whole game flow is now a tree you can read. Reordering the tutorial means moving two items in a list. Removing the finale for a demo build means removing one branch. Testing the night sequence means starting that sequencer directly, without playing the tutorial first.

The Contract Is the Interface, Not the Type

There is a subtle decision hidden in the previous section. The sequencer does not ask “is this an executor?”. It asks “can this be started, and does it announce when it finishes?”.

That difference matters because it lets the sequencer orchestrate things that were never designed as executors. A creature that walks a path and announces when it reaches the end, an animation player that announces when a clip ends, a door that announces when it is opened: all of them can join a sequence, as long as they expose the two halves of the contract.

It also gives the sequencer a natural vocabulary for three kinds of children:

  • Blocking executors start and hold the sequence until they finish;
  • Fire-and-forget executors start and let the sequence continue at once, which is a cheap way of running things in parallel (an ambient sound, a flickering light);
  • Non-executors are ignored, so helpers and data can live next to the executors without breaking anything.
NoteExplicit beats implicit, eventually

Checking capabilities at runtime is flexible and fast to prototype with. As the project grows, a formal contract (an interface, a protocol, a trait, whatever your language calls it) catches mistakes earlier, such as a misspelled event name that silently turns a blocking executor into a fire-and-forget one. A good middle ground is to keep the flexible check in the sequencer but log every child it skips or does not wait for.

Waiting for Many: Aggregating Executors

Some moments are not a single action but a group of them. Picture a scene where several figures walk past the player, one after another, and the moment is only over when every one of them has left.

The executor that represents this moment is itself a small orchestrator: it spawns its children at an interval, counts how many finished and only finishes when both counts reach the target.

Two details deserve attention. First, the check happens on both counters: if a child finishes very quickly, before the last one is spawned, the executor must not finish early. Second, the spawn loop checks whether the executor is still running before each spawn, because something else may have finished or interrupted it in the meantime.

Children can also relate to each other. In my case, each spawned figure follows the one in front of it, which turns a list of independent entities into a procession without any extra orchestration.

Readiness Barriers: Making Sure the World Is Ready

Executors assume the world is in place: assets loaded, settings applied, references resolved. When loading is asynchronous, a common source of bugs is an executor starting before what it needs exists.

The same event-driven thinking solves this. Each loader registers itself when it starts, announces when it finishes and a global registry announces when all of them are done.

The most important line in this diagram is the consumer asking before subscribing. Events are not stored: if a consumer subscribes after the loader has already finished, it will wait forever for an event that already happened. This is the late subscriber problem, and the fix is always the same: check the current state first, subscribe only if the result is not there yet.

The other detail is the coalesced check. When several loaders finish in the same frame, the registry schedules a single “are we all done?” check for later in the frame, instead of evaluating it once per loader. The event fires once, at the right moment.

Interactions as Event Sources

So far, executors finish because of their own conditions. The other half of a game is the player doing things: pressing a button, opening a gate, pulling a lever. Those interactions should not call gameplay code directly either. They should become events.

The layering matters. A generic interactable only knows “I was interacted with”. The object that owns it translates that into something meaningful, such as “the gate was opened” or “the lever was pulled”, and only then does gameplay react. Each layer can be reused without the ones above it: the same interactable powers a button, a drawer or a window, and the same opened event can finish an executor, change a light or trigger a sound.

Draggable objects follow the same idea with a slightly richer state machine:

Grabbing an object that is still settling simply starts a new drag, exactly as it would from Idle. Every transition emits a state change event, so a door that slams shut on its own, a locked drawer that rattles or a gate that reaches its limit can all be expressed without the drag logic knowing anything about horror.

Variation Through Data

In a horror game, predictability kills tension. The flow must be readable for the developer and unreadable for the player. The way to get both is to keep the structure fixed and move the variation into data.

Two simple tools go a long way:

  • Profiles: a session description (short, medium or long, for example) that a sequencer reads to decide how many moments to run and how dense they are;
  • Weighted choices: every candidate (a creature, a sound, a texture variation, a line of dialogue) carries a weight, and selection is proportional to it.

Selection walks the list accumulating weights and returns the first candidate whose running sum exceeds the draw, so each candidate wins with a probability proportional to its weight. When every weight is zero, the first candidate is returned instead of failing.

Combined with executors, this turns content design into tuning. A rare scare is a candidate with a low weight. A night that escalates is a profile with denser sequences. None of it requires new code.

Evolving the Engine: What Comes Next

A sequential runner with blocking and fire-and-forget children already covers a surprising amount of a game. But once the contract is stable, the same idea extends naturally, and each extension is just another executor that orchestrates executors:

If this family looks familiar, it is because it converges towards behaviour trees3, with one important difference in intention: here the tree describes the pacing of the game, not the decisions of an agent.

Three improvements to the base contract are worth making before the family grows:

  1. Cancellation. In a horror game, the player can be caught in the middle of anything. Executors need a cancel path, distinct from finish, that cleans up without triggering the next moment. Composites propagate it to their running children.
  2. Reset. An executor that can only run once cannot be reused by a Repeat or replayed after a checkpoint. Resetting state and counters should be part of the contract.
  3. Shared context. Executors frequently need the same references: the player, the main camera, the current session. Looking them up globally from every executor couples them to the world layout. Passing a context (often called a blackboard) from the sequencer down to its children keeps executors portable and makes them trivial to test.

With cancellation in place, the state machine gains one more exit:

Cancellation can arrive at any point before the executor ends, and a reset brings either ending back to the start.

And because every transition is an event, tracing comes almost for free: logging each start, finish, skip and cancel with the executor’s path in the tree gives you a timeline of every session, which is invaluable when a playtester says “it just stopped”.

Classified Segmentation: Organising the Project

An executor architecture only stays modular if the project structure reflects it. When base classes, concrete moments, global services and data all live in the same folder, the boundaries that the code works so hard to keep start to blur.

The approach I settled on is to classify every piece by its nature first, and by its subject second:

A handful of rules make this classification hold over time:

  • One class per folder, named after it, with its visual or scene definition beside it when it has one;
  • Subclasses of a base in the same layer go in a plural folder inside the base’s folder (Loader/Loaders/...), so the family is visible at a glance;
  • Concrete implementations of a core base live in Features, grouped by what they are (Executors/Walk, Executors/Cutscene), never by the level where they first appeared;
  • Helpers that only exist for one class stay in that class’s folder until something else uses them, at which point they earn their own;
  • Dependencies point inwards: Features may depend on Core, Core never depends on Features.

The last rule is the easiest to break and the most important to keep. The moment a core system references a concrete feature, for example the base executor looking up the player, it can no longer be reused in another game or tested without the whole world around it. The shared context described in the previous section is precisely what removes that last dependency.

TipA quick test for your structure

Pick any folder in Core and imagine copying it into a completely different game. If it does not compile, or does not make sense, without something from Features, the boundary has leaked.

Trade-offs

The model is not free, and its costs should be weighed before adopting it:

  • Indirection. The flow is no longer visible in the code of any single piece. Without tooling (a readable tree in the editor, tracing in the logs), “why did this happen now?” becomes harder to answer, not easier;
  • Event chains are harder to debug than calls. A missing or misnamed completion event does not raise an error; it simply never arrives. Logging skipped children and executors that stay Started for too long is the countermeasure;
  • Fail forward hides failures. It keeps the session running, but only logging makes the skip visible, and critical executors should opt out of it;
  • Over-generalisation. Not every behaviour is a moment in a flow. Continuous systems (movement, physics, ambient simulation) belong in the regular update loop, and wrapping them as executors only adds ceremony;
  • Granularity. Executors that are too small turn sequences into long lists of trivial steps; executors that are too large reintroduce the coupling the model was meant to remove. A useful heuristic is one executor per completion condition the designer cares about.

Conclusion

The architecture described here moves the gameplay flow out of the individual pieces and into an explicit, composable structure:

  • A minimal executor contract (start, update, announce the end) with a lifecycle owned by a base and behaviour supplied through hooks;
  • Composition through executors that orchestrate executors, starting with the sequencer and extending to parallel, selector, repeat and decorator variants;
  • Events as the only coupling between pieces, from completion and readiness to player interaction;
  • Data as the source of variation, through profiles and weighted choices;
  • A classified project structure, by nature first and subject second, with dependencies pointing inwards.

The result is a game loop that describes what happens, while each executor decides how.
